# ADR-003：以能力权限决定确认门

**状态：** 部分被 ADR-004 替代  
**日期：** 2026-08-09  
**决策者：** 用户确认，研发负责整理  
**关联需求：** FR-005、FR-008、AC-003、AC-007  
**关联决策：** ADR-001、ADR-002；实现范围见 ADR-004

## 背景

任务锚定解决“用户要处理什么”，但并不自动回答“Agent 能否执行”。此前表述容易把“外部或不可逆动作”解释成无论权限如何都需要再次确认，导致用户已经说“继续”或完成澄清后，Agent 仍多问一次。

这会损害通用 Agent 的连续性：用户的明确任务请求本身就是意图授权；是否可实际执行，应由 Agent 当前拥有的工具、账号和策略能力决定。

## 选项

### 选项 A：按动作副作用类型一律二次确认

- **优点：** 表面上保守。
- **缺点：** 忽略已有用户指令和已授能力；造成重复确认、任务停滞和差的操作体验。
- **结论：** 不采用。

### 选项 B：只要任务锚定成功就执行

- **优点：** 流畅。
- **缺点：** 忽略工具是否启用、账号是否授权、策略是否允许和目标是否超出任务范围。
- **结论：** 不采用。

### 选项 C：用户意图授权与能力权限双重成立后直接执行

- **优点：** 既保留任务连续性，也尊重真实权限边界；确认仅在确有权限缺口时出现。
- **缺点：** 若在意图层新建权限接口，会扩大改造范围并与现有工具权限逻辑重复。
- **结论：** 采用。

## 决策

执行准入必须同时满足：

```text
已锚定任务范围内的用户意图授权
        +
当前工具/账号/策略允许的能力权限
        =
直接执行
```

“继续”“照这个办”和对澄清问题的明确回答，均可延续已选任务范围内的用户意图授权。只要能力权限允许，Agent 直接执行，不因邮件、发布、删除、付款或其他副作用类别而默认增加确认轮次。

原设想的能力判定接口不在本改造中实现；其职责由现有运行机制继续承担。ADR-004 收紧了这一实现范围。

如现有运行机制已提供能力判定，可采用类似下列结果：

| 能力结果 | 行为 |
| --- | --- |
| `permitted` | 直接执行。 |
| `confirmation_required` | 仅针对策略要求的范围提出确认；确认后执行。 |
| `unavailable` / `denied` | 不执行；说明缺失的工具、账号、策略或范围，并给出可恢复路径。 |

绝对安全拒绝仍优先于用户指令；本 ADR 不允许绕过平台、账户或系统的真实权限限制。

## 后果

### 正面后果

- 已确认任务可真正连续推进，避免多余的“你确定吗”；
- 将风险控制放回可配置、可审计的能力策略，而非模糊的副作用标签；
- 同一模型可以适用于本地文件、邮件、发布、支付和代码操作等通用领域。

### 代价与风险

- 权限行为仍依赖现有运行机制，意图层不得假定、放宽或覆盖其作用域；
- 需要保证重试、续办和 subagent 回传不会导致重复外部执行；
- “confirmation_required” 的来源与展示需对用户可解释。

## 重新审查条件

- 能力权限粒度无法表达常见工具的真实边界；
- 真实使用显示确认不足导致不可接受的误操作；
- 平台或合规要求规定某类操作必须逐次确认。
