# 意图理解与调度需求

**版本：** v0.8  
**状态：** 已确认基础规则；轻量优先基准已确认，旧实施设计不再作为开发依据  
**更新日期：** 2026-08-10

**本次变更：** 以 ADR-009 固化“轻量优先、三车道、快速路径零侵入”基准。意图识别是逻辑准入，不等于每轮新增独立模型调用；执行规划和持久任务状态仅限复杂、跨回合或后台任务。旧桥接方案须按本需求重写后，方可重新进入开发判定。

## 1. 问题定义

当前普通自然语言消息会直接进入主模型及工具循环。模型同时隐式承担用户理解、执行决策、任务拆分、工具选择和 subagent 委派，缺少可检查的任务对象锚定与调度门。这会使系统在上下文没有任务对象、或存在多个无关对象时，仍可能盲目行动。

目标用户希望 nanobot 是主动但不冒进的通用 Agent：应能利用明确上下文继续任务，也必须在对象或关系不足时停下澄清。

## 2. 术语

| 术语 | 定义 |
| --- | --- |
| 有效上下文 | 当前消息、直接回复或附件、待澄清事项、活动任务、已确认任务列表/任务图等能被明确指向的状态；不包括为了寻找目标而任意翻查的全量历史或外部世界。 |
| 任务对象 | 可被定位并被动作作用的文件、链接、会话事项、项目、账户、任务、附件或其他实体。 |
| 任务帧 | 对一个已锚定任务的结构化描述，包含目标、对象、约束、授权、未决项与状态。 |
| 任务图 | 已确认的任务列表及其顺序、依赖、并行或其他关系。 |
| ready 工作单元 | 任务图中当前满足前置条件、可以被推进的一个或多个工作单元。 |
| 执行前沿 | 当前唯一可解释的任务对象，或一个关系明确任务图中的 ready 工作单元集合。 |
| 意图结果 | 前置层对本轮用户请求的结构化理解：消息行为、任务/对象锚定、范围、约束、证据及澄清结果；不包含执行组织。 |
| 执行图 | Runner 为当前已确认任务生成的短生命周期工作 DAG；节点包含交付物、依赖和执行者（主 agent 或 subagent）。 |

## 3. 功能需求

### FR-001：命令与系统消息优先路由

系统必须先保留现有确定性命令和内部系统消息处理边界。此类消息不进入自然语言任务锚定流程。

### FR-002：上下文优先的对象锚定

对普通用户消息，系统必须在规划、工具调用或 subagent 调度前，依据有效上下文解析任务对象和当前执行前沿。意图结果必须包含上下文证据、范围与澄清状态，但不得提前决定 subagent 数量、执行者或串并行组织。

### FR-003：无对象时停止

当没有任何可解析任务对象、活动任务或已确认任务图时，系统必须只提出一个聚焦澄清问题。不得以“只读侦察”为由调用工具、搜索历史、访问网络或创建 subagent。

### FR-004：歧义时停止

当存在多个彼此无关的候选任务对象，或多个 ready 工作单元没有明确关联关系时，系统必须澄清用户要推进的对象或优先级。不得按最近提及、模型偏好或成本猜测自动选择。

### FR-005：唯一任务自动续办与意图授权延续

当有效上下文中存在唯一、未完成、已展示给用户的任务帧时，用户使用“继续”“照这个办”等省略表达可被解析为该任务的续办，并延续该任务范围内已确认的用户意图授权。若当前 Agent 对目标动作具备能力权限，系统应直接执行；不得仅因动作具有外部副作用而重复询问。

### FR-006：任务图按关系推进

当有效上下文中存在已确认的任务图时，系统必须依据其中声明的顺序、依赖和并行关系推进 ready 工作单元。多个 ready 点只有属于同一任务图且关系明确时，才可不经额外澄清进入规划。

### FR-007：Runner 内的执行图与委派规划

Runner 接收可推进的意图结果后，必须先判断任务走快速车道还是编排车道。唯一、单步骤、无依赖、无并行收益且无需后台续办的任务，直接复用既有 Runner 执行，不得因新增能力而强制创建持久任务图、调用 Planner 或创建 subagent。只有多目标、存在依赖/写入冲突、可并行收益、跨回合续办或后台工作时，才生成执行图。

编排车道的执行图依据工作单元的依赖、独立性、资源收益、工具能力、写入冲突和预算，为节点分配主 agent 或 subagent 执行者；主做、子 agent 串行、子 agent 并行、主子并行均是执行图的不同形态，而不是意图类别。

subagent 只能接收已锚定、范围明确、验收可描述的工作单元；“任务复杂”本身不足以成为委派理由。

### FR-008：复用既有能力权限机制

本改造不新增、替换或重解释 nanobot 现有的工具、账号、策略和确认机制。意图层只提供已锚定的任务范围与语义；Runner 负责执行图规划，随后继续由既有运行机制处理工具可用性、权限、确认和真实执行结果。

### FR-009：可解释性

系统对“继续、澄清、规划或委派”的决策必须可追溯到对象、任务图关系或用户明确指令；后续 WebUI 可展示简短理由，但不得泄露内部提示词或敏感上下文。

### FR-010：subagent 结果会话归属隔离

每个后台 subagent 必须在启动时捕获其父会话的**有效 session key**，并将其作为唯一结果归属。结果从产生、消息总线投递、pending queue 回注、会话持久化到模型上下文的每一步均必须保持该归属。

系统必须在消费内部 `subagent_result` 前校验“任务登记的父会话键 == 消息目标有效会话键”；若不相等、归属缺失或任务未知，必须隔离并记录错误，且不得将结果写入任何会话历史、交给任何主 agent 或作为用户可见回复。不得根据最近活跃会话、相同 chat ID、统一会话默认值或模型猜测改投其他会话。

### FR-011：既有运行时兼容与默认零影响

意图识别与执行图能力必须以默认关闭的 feature flag 接入。关闭时，普通消息必须走当前 `restore → compact → command → build → run → save → respond` 路径，不产生额外模型调用、任务状态写入、工具行为、subagent 事件或 memory 变化。

开启时，新增层只能：

- 在现有运行机制前产生 `IntentResult` 和短生命周期 `ExecutionPlan`；
- 将计划约束作为受控输入交给既有 Runner；
- 为已计划 subagent 补充计划归属与会话所有权校验。

不得替换或改变 `AgentRunner` 的工具循环、Session 历史和压缩、Dream memory、工具权限/确认、provider 会话状态、subagent 工具隔离、取消语义或 WebUI 既有事件协议。任何对共享 Runner API 的扩展必须默认值完全保持原语义。

### FR-012：无执行分支的会话完整性

意图结果为 `clarify` 或 `reply` 时，系统必须不调用业务工具、Planner 或 subagent，但必须通过受控的既有会话收尾准确持久化本轮用户输入与对应答复。意图调用本身不得作为普通 assistant 历史、provider state 或 memory 内容写入。该分支不得触发 memory consolidation。

### FR-013：计划级结果隔离与一次性消费

subagent 结果除必须满足 FR-010 的会话归属外，还必须绑定创建它的 `plan_id` 与计划节点。只有父会话当前活跃计划的 `plan_id` 完全匹配时，结果才可进入该回合的模型上下文。合法但不匹配、或父回合已结束的结果必须作为原任务的延后完成证据保存，且不得自主向用户发出答复；非法或重复结果必须隔离。每份合法结果最多向模型回注一次。

### FR-014：计划完成前不得伪最终答复

当执行计划仍有必需节点未完成时，系统不得把主 agent 的候选终答作为最终回复显示给用户。计划成功汇合后才可提交整合答复；发生失败、取消、容量阻塞、超时或迭代上限时，只能提交明确标识未完成原因的答复。

### FR-015：任务帧、澄清态与计划生命周期

未锚定信息的 `ClarificationState` 与可执行 `TaskFrame` 必须分离：前者可处于 `clarifying`，不得被“继续”视为任务；后者至少有 `ready`、`running`、`waiting_results`、`completed`、`blocked`、`cancelled` 状态及合法迁移。执行计划是一次运行切片；用户改变范围、出现替代路径、取消、进程终止或重规划时必须产生或终结明确的 `plan_id`，旧计划未消费结果不得自动满足新计划。

### FR-016：轻量优先与三车道

系统必须将普通回合优先保持在快速车道：不新增独立 Planner 调用、不创建持久 `TaskFrame`/`ExecutionPlan`、不创建 subagent，且除任务准入所必需的受控判断外，不增加额外 LLM 往返。命中 skill 时，所有 active skill 默认可成为候选，但只向执行上下文注入最终绑定的少量 skill 正文；无命中时不得产生 skill 正文注入。

只有任务结构证明存在拆分、并行、后台或跨回合收益时，才可进入编排车道。skill 选择不得改变既有 ToolRegistry、MCP 注册、权限、确认或 memory 语义；普通 tool/MCP 不是推荐加载对象，仍由既有 Runner 在执行时选择和调用。

## 4. 业务规则

```text
候选对象 / 任务结构
  ├─ 无 → 澄清
  ├─ 唯一任务帧 → 任务理解与规划
  ├─ 已确认任务图，ready 点关系明确 → 按关系规划
  └─ 多个无关候选，或 ready 点关系不明 → 澄清
```

对象证据优先级候选如下，后续以 ADR 固化：当前用户显式指向 > 直接回复/附件 > 待澄清事项的回答 > 唯一活动任务帧 > 已确认任务图。

## 5. 非目标

- 不把所有用户消息强行归入固定意图类别；
- 不让 LLM 自由产生“我认为应该执行”的不可审计结论；
- 不将 `generalist` 或其他 subagent 角色作为不确定任务的兜底容器；
- 不在本阶段定义数据库、模型供应商、提示词细节、工作树隔离或 UI 视觉方案；
- 不要求多个 ready 工作单元一定并行执行。

## 6. 验收标准

| 编号 | 验收标准 |
| --- | --- |
| AC-001 | 输入“帮我把这件事处理一下”，且有效上下文没有对象时，系统仅澄清，零工具调用、零 subagent。 |
| AC-002 | 有两个无关未完成事项时，输入“继续”必须请求选择，不得自动执行任一事项。 |
| AC-003 | 存在唯一活动任务帧时，输入“继续”可恢复该任务并交给既有运行机制执行；意图层不得因动作类型额外插入确认。 |
| AC-004 | 关系明确的任务图中存在多个 ready 工作单元时，系统按图关系生成推进计划；若关系不明则澄清。 |
| AC-005 | 任何被派发的 subagent 工作单元均可回溯到意图结果、执行图节点、范围与验收条件。 |
| AC-006 | 对同一会话回放，锚定结论、澄清/规划分支和记录的理由应可复核。 |
| AC-007 | 已明确“向客户发送已拟定邮件”的唯一任务，用户回答“继续”或完成对象澄清后，意图层将该任务直接交给既有运行机制；发送、确认、失败处理均保持既有能力权限语义。 |
| AC-008 | 对同一明确任务，Runner 可生成主做、子 agent 串行、子 agent 并行或主子并行的执行图；其节点依赖和执行者分配可被复核，且意图结果本身不包含该分配。 |
| AC-009 | 同时存在有效会话键 A 与 B（A ≠ B）时，A 派发的 subagent 结果只可进入 A；即使 B 正在运行、A 已空闲或 chat ID 相同，B 的 pending queue、历史、模型请求和用户输出均不得出现该结果。若统一会话配置已将两者显式合并为同一有效键，则不属于本验收场景。 |
| AC-010 | 新 feature flag 关闭时，现有普通消息、命令、系统消息、/goal、memory 压缩、工具调用、subagent 生命周期和 WebUI 事件的既有回归测试保持通过，且意图/计划模块不被调用。 |
| AC-011 | feature flag 开启时，意图与执行图的新增状态不改变 Session 历史、Dream memory 或 provider 会话状态的既有数据格式；规划失败时可安全降级，但不得回退为无锚定的自由委派。 |
| AC-012 | `clarify` 和 `reply` 回合均持久化用户输入与用户可见输出，但不调用 memory consolidation、Planner、业务工具或 subagent，也不写入 provider state。 |
| AC-013 | 同一有效会话中的计划 A、B 交叠时，A 的结果不进入 B 的 pending queue、模型上下文或终答；A 父回合结束后的合法结果仅作为 A 的延后完成证据，待用户恢复 A 时再消费。 |
| AC-014 | subagent 完成公告与运行登记清理竞争时，合法结果仍能经独立所有权收据被消费一次；重复、未知、跨会话或字段不一致结果均不写历史、不注入模型、不输出用户可见消息。 |
| AC-015 | 主子并行时，主 agent 的候选终答在必需子节点完成前不会流式显示为最终结果；失败、取消、阻塞或超时时的最终文本明确说明未完成。 |
| AC-016 | 用户“停止”、范围修改、进程中断与重规划后，旧 `plan_id` 不能满足新计划；用户“继续”只从同一 TaskFrame 已确认的完成证据重新规划。 |
| AC-017 | 明确的单步骤任务在 feature flag 开启时不调用 Planner、不创建 subagent、不建立持久任务图，仍由既有 Runner 和既有权限语义直接执行。 |
| AC-018 | 快速车道不增加独立 LLM 往返；若采用意图控制，其必须与原有首轮调用合并或以确定性代码完成，并以回放用量验证。 |
| AC-019 | 用户添加或按用户明确要求创建的 active skill 默认参与自动候选；仅最终绑定的少量 skill 正文进入当前执行上下文，`$skill` 仍可强制本轮加载。 |
| AC-020 | 没有 skill 命中时，系统不注入任何 skill 正文；没有复杂任务结构时，系统不展示或持久化编排噪音。 |

## 7. 已知事实、假设与未决问题

### 已知事实

- 现有 nanobot 对斜杠命令有确定性路由；普通消息没有独立的任务锚定阶段；
- 现有 `/goal` 是显式长期目标能力，而不是自然语言任务理解；
- 现有 subagent 为通用执行者，只接收父 agent 提供的任务文本。

### 假设

- 结构化的任务理解结果能显著降低无效工具调用和无效委派；尚需评测验证；
- 任务图可成为通用 Agent 跨领域任务续办的共同表示；其数据模型尚未决定。

### 未决问题

- 结构化评估使用何种模型与成本/延迟预算；
- 灰度阶段多个可并行工作单元的实际容量与成本阈值；
- 用户如何查看、修正或取消任务图；
- 评测样本集、指标与上线灰度策略。
