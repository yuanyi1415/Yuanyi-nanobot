# 意图识别与执行规划成本纸上测算

**状态**：历史纸上测算；输入假设已被 ADR-009 暂停，不作为方案成本结论  
**日期**：2026-08-10  
**关联**：[意图理解与调度需求](../01_需求/意图理解与调度需求.md)、[执行图最小桥接方案](../03_方案/执行图最小桥接方案.md)、[V1 实施前回放用例](../04_评测/V1实施前回放用例.md)

> **状态说明（2026-08-10）**：本文假定独立的轻量意图调用和固定 Planner 输入；后续已确认每层必须使用受控事实包，并采用快速车道优先。因此本文中的 84.7%、29% 和 52% 仅保留为旧假设的可复算样本，不能用于评估或批准新方案。新方案完成输入契约后，必须以真实回放重算。

## 1. 目的与结论

本记录评估在 nanobot 原生 `AgentLoop → AgentRunner` 之前增加“意图识别”，并在复杂任务中增加“执行规划”后，模型调用成本是否能由减少的空转与上下文膨胀抵消。

**结论**：

1. 意图识别应常驻。对“没有可执行对象”的消息，它可用小上下文完成澄清，避免启动一次完整 Runner；在本记录的保守假设下，单次约节省 84.7%。
2. 不应对每个已就绪任务无差别调用 LLM 执行规划。清晰的单步骤任务若强制规划，成本约增加 29%。
3. 对多目标、长工具链、可独立并行的复杂任务，受限子任务与压缩回传可显著抑制主会话上下文增长；双分支调研样本中，纸上成本约降低 52%。
4. V1 应采用“意图层常驻，规划层按复杂度触发”的策略；能力候选检索必须是本地元数据逻辑，不增加一个 skill/MCP 匹配 LLM 调用。

## 2. 计价口径与边界

### 2.1 价格口径

以下价格由用户在本次讨论中指定，未在本记录中另行验证：

| 项目 | 单价（人民币 / 1M token） |
| --- | ---: |
| 输入，缓存命中 | 0.02 |
| 输入，缓存未命中 | 1.00 |
| 输出 | 2.00 |

计算公式：

```text
成本（元） = (未命中输入 × 1 + 命中输入 × 0.02 + 输出 × 2) / 1,000,000
```

### 2.2 保守假设

- 每个新阶段的第一次调用按输入缓存未命中计算；不把不同提示词结构的意图、规划、Runner 调用视为可共享缓存。
- 同一 Runner 工具循环中，稳定的系统前缀可命中缓存；新加入的工具结果和本轮材料按未命中计算。
- 意图识别输入为 3,500 token、输出 120 token；执行规划输入为 4,500–5,000 token、输出 180–200 token。这是目标预算，而非当前实现的实测值。
- V1 保留现有完整 ToolRegistry，不把“能力候选/绑定”虚构为已经减少 Runner 工具定义输入。因此，下文没有计算该项潜在节省。
- 金额只覆盖 LLM token 费用，不包括搜索、MCP、邮件、存储、网络和基础设施成本。

## 3. 纸上回放

### 场景 A：对象缺失，应该澄清

用户消息：“帮我看看这个。”上下文中没有可解析的对象或唯一待推进任务。

| 模式 | 调用假设 | 成本 |
| --- | --- | ---: |
| 当前 nanobot | 主 LLM：24,000 未命中输入 + 200 输出；最后只能反问 | ¥0.02440 |
| 改造后 | 意图 LLM：3,500 未命中输入 + 120 输出；输出一个澄清问题 | ¥0.00374 |

**结果**：单次节省 ¥0.02066，约 **84.7%**。

说明：若完整 Runner 的系统前缀恰好命中缓存，原生回合约 ¥0.00480，节省会缩小至约 22%。因此该收益依赖真实缓存命中率，不能视为固定值。

### 场景 B：明确单步骤外部动作

用户消息：“给客户张三发送本周项目进度邮件。”假定现有权限和工具策略允许直接执行，Runner 需要一轮工具调用和一轮最终回复。

#### 当前 nanobot

| 调用 | 计价 | 成本 |
| --- | --- | ---: |
| Runner 第 1 轮 | 24,000 未命中输入 + 200 输出 | ¥0.02440 |
| Runner 第 2 轮 | 20,000 命中 + 5,000 未命中输入 + 350 输出 | ¥0.00610 |
| 合计 |  | **¥0.03050** |

#### 若每个 ready 任务均强制经过 LLM 规划

| 调用 | 计价 | 成本 |
| --- | --- | ---: |
| 意图识别 | 3,500 未命中输入 + 120 输出 | ¥0.00374 |
| 执行规划 | 4,500 未命中输入 + 180 输出 | ¥0.00486 |
| Runner | 保持原有两轮，并增加少量计划约束 | 约 ¥0.03080 |
| 合计 |  | **约 ¥0.03940** |

**结果**：约增加 ¥0.00890，即 **约 29%**。这类任务没有值得拆分或重排的执行结构，LLM Planner 的收益不足以覆盖费用和延迟。

### 场景 C：复杂、可并行的双分支调研

用户消息：“调研三款主流 Agent 的 subagent 调度和 skill 激活机制，给 nanobot 形成方案建议。”

假定原生主 Agent 自行搜索、阅读、整理，需要六轮调用；工具结果持续回填，使未命中上下文逐轮增长。

#### 当前 nanobot：主 Agent 串行完成

| 调用 | 成本 |
| --- | ---: |
| 第 1 轮：28,000 未命中输入 + 工具调用 | ¥0.02840 |
| 第 2–5 轮：稳定前缀命中，工具结果逐轮累积 | ¥0.06280 |
| 第 6 轮：整合结论 | ¥0.02740 |
| 合计 | **约 ¥0.11860** |

#### 改造后：两个受限子任务并行，父 Agent 汇总

| 调用 | 计价 | 成本 |
| --- | --- | ---: |
| 意图识别 | 3,500 未命中输入 + 120 输出 | ¥0.00374 |
| 执行规划 | 5,000 未命中输入 + 200 输出 | ¥0.00540 |
| 两个子 Agent | 各两轮、每个仅携带本分支约 8,000 token 初始输入 | ¥0.02324 |
| 父 Agent 汇总 | 压缩子结果后生成结论 | ¥0.02460 |
| 合计 |  | **约 ¥0.05698** |

**结果**：约节省 ¥0.06162，即 **约 52%**。

节省来源不是“子 Agent 免费”，而是每个工作者只带必要上下文，父 Agent 只消费压缩且有验收条件的结果，避免单一主会话不断累加所有原始网页与工具输出。

## 4. 设计含义

| 任务状态 | 意图 LLM | 规划 LLM | 执行策略 |
| --- | ---: | ---: | --- |
| 直接问答或闲聊 | 是 | 否 | 意图层可直接回复，不进入完整 Runner |
| 无对象、多点且无关联 | 是 | 否 | 只产生一个澄清问题，不分配执行资源 |
| 已锚定且明确的单步骤任务 | 是 | 否或本地单节点计划 | 复用原生 Runner 直接执行 |
| 多目标、存在依赖/冲突/并行可能 | 是 | 是 | Planner 生成并经代码校验的执行图 |
| 已有任务图后的“继续” | 是 | 仅在需要重排时 | 按 ready 节点恢复执行 |

这里的“本地单节点计划”是保守优化：仅在任务已唯一锚定、无依赖、无并行候选、无需委派时使用。不能确定时仍进入 LLM Planner；它不替代语义理解，也不允许代码擅自扩大任务范围。

## 5. 成本门槛与实施建议

1. **意图调用限额**：固定小输入预算，禁止携带完整工具 Schema、全部 skill 正文、长工具结果或完整历史。
2. **规划调用门槛**：仅当出现多个交付物、显式/隐式依赖、多个候选能力、可并行工作、已有计划需重排或主会话上下文明显膨胀时调用。
3. **子任务回传限额**：回传应是证据、结论、失败原因和引用，不应把原始检索日志整段注入父会话。
4. **拒绝虚假节省**：V1 不动态收窄 ToolRegistry，不能把未来“节点级工具暴露”带来的 token 节省计入当前商业论证。
5. **灰度计量**：隔离开发完成后，记录每个阶段的未命中/命中输入、输出、调用次数、子任务数、上下文长度、端到端时延和任务成功率；再用真实回放决定阈值。

## 7. 验证记录

- **本体**：确认新增意图与规划调用的货币成本，是否能由减少的空转与上下文膨胀抵消。
- **高风险点**：缓存命中被高估；简单任务被强制规划；把能力候选当作免费；忽略子 Agent 回传 token。
- **逐点验证**：按冷启动前置调用计价；场景 A 节省约 84.7%；场景 B 强制规划增加约 29%；场景 C 双分支复杂调研节省约 52%。
- **实测信号**：所有金额可由第 2.1 节公式、表中 token 假设复算；本记录尚无真实 Provider usage 数据。
- **未验证项**：真实提示词体积、缓存命中率、工具结果规模、子 Agent 回传长度和端到端时延，均须在隔离开发环境通过回放埋点确认。
