# 桥接方案与当前基线冲突审查

**日期：** 2026-08-10  
**状态：** 已完成源码审查；不改变现有方案、需求或 ADR 状态  
**审查对象：** [执行图最小桥接方案](../03_方案/执行图最小桥接方案.md) v0.2  
**方法：** 只读追踪 `AgentLoop`、`AgentRunner`、`SubagentManager`、`SpawnTool` 与配置；未改动运行时代码、配置、会话或网关。

## 1. 结论

桥接方向本身与 nanobot 的核心分层**不冲突**：意图在业务执行前完成，`AgentLoop` 仍拥有会话和 subagent，`AgentRunner` 仍是通用工具循环，`SubagentManager` 仍负责既有生命周期。

但 v0.2 的接口描述还不足以安全进入实施。存在 5 个会导致行为错误或数据串扰的 P0 缺口，以及若干 P1 边界未定义。它们不是“多补几个测试”能兜住的细节，必须先补入方案并冻结相应契约；否则会出现：澄清轮丢失会话事实、旧计划结果注入新计划、结果抢跑显示为最终答复、或子任务完成后无法完成所有权校验。

因此建议：**保持 v0.2 的总体方向和待评审状态；先完成本审查中的 P0 修订，再讨论定案。**

## 2. 已确认的基线事实

| 基线事实 | 源码证据 | 对桥接的含义 |
| --- | --- | --- |
| 普通回合是 `restore → compact → command → build → run → save → respond`。 | `nanobot/agent/loop.py`：`_process_message()` | 前置意图层必须插入，但不能跳过现有会话写入和交付收尾。 |
| `runtime` 在 `_build_turn()` 中才选择并写入 `TurnContext`；同一方法还会进行内存整合、运行时上下文解析、provider 状态暂存和用户消息早期持久化。 | `nanobot/agent/loop.py`：`_build_turn()` | 不能直接把需调用 LLM 的意图阶段塞在 `build` 之前。 |
| 活跃会话只有一个按 `session_key` 索引的 pending queue；任何同键入站消息都会进入它。 | `nanobot/agent/loop.py`：`_pending_queues`、`run()`、`_drain_pending()` | 当前队列不认识 `plan_id`，不能天然实现“只汇合本计划”。 |
| `_drain_pending()` 以“该会话仍有 subagent 运行”为等待条件，最长等待 300 秒。 | `nanobot/agent/loop.py`：`_drain_pending()` | 这是会话级粗汇合，不是计划级精确汇合。 |
| 子任务完成公告会带 `session_key_override`，但元数据仅有 task id 等信息，没有 plan id。 | `nanobot/agent/subagent.py`：`_announce_result()` | 发布侧已有正确会话路由基础，但缺少计划归属与消费侧校验。 |
| 任务结束回调立即从 `_running_tasks`、`_task_statuses`、`_session_tasks` 移除登记。 | `nanobot/agent/subagent.py`：`spawn()` 内 `_cleanup()` | 不能在消息消费者处再依赖这些临时表做 task 所有权校验。 |
| 流式 token 在 provider 返回时即经 `hook.on_stream()` 外发；最终回复后才检查注入并决定是否续办。 | `nanobot/agent/runner.py`：`_request_model()`、`_try_drain_injections()` | “完成门”不能仅放在最终回复后的 injection 点。 |
| `SpawnTool` 在执行时才检查全局并发数；默认上限为 1。 | `nanobot/agent/tools/spawn.py`；`nanobot/config/schema.py` | 规划时看到的空闲容量不能保证 spawn 时仍可用。 |

## 3. P0：实施前必须补齐的冲突与漏洞

### P0-1：意图阶段位置与 runtime／持久化生命周期冲突

v0.2 建议的顺序是 `restore → compact → command → interpret → build`，而 `IntentRecognizer` 又需要复用当前 LLM runtime。现有 runtime 只在 `build` 中选定；若直接提前调用模型，`ctx.runtime` 不存在。若反过来先执行完整 `build`，则在“无对象只澄清”的回合也可能触发内存整合、provider 状态处理和用户消息持久化，违背“先判断是否有资格执行”的最小副作用边界。

更关键的是：澄清或直答如果在 `build` 前直接结束，将绕过当前用户消息的持久化与既有交付收尾；若临时复制一套写入逻辑，容易与恢复检查点、会话历史或 provider state 产生双写/漏写。

**推荐修正：**把 `build` 拆成两个内部阶段，而不是重写 Runner：

```text
restore → compact → command → prepare_intent_runtime → interpret
  ├─ clarify / reply：复用统一的 no-run 持久化与交付收尾
  └─ ready：complete_build → plan → run → save → respond
```

`prepare_intent_runtime` 只负责选择 runtime、构造受限的输入快照；不得进行内存整合、工具上下文构建、provider state 暂存、业务工具调用或用户历史写入。`complete_build` 继续承接原 `_build_turn()` 的其余行为，确保 ready 路径仍走既有业务运行机制。

### P0-2：`plan_id` 精确汇合无法直接建立在现有 pending queue 上

同一有效 session 的所有内部结果和用户追问目前都会进入同一个 pending queue。若本计划运行时收到了同会话旧计划的结果，简单地在 `_drain_pending()` 过滤它会造成三种错误：丢弃消息、反复 requeue 形成忙循环，或最终被错误注入当前模型上下文。若当前计划没有活跃父回合，结果甚至会走独立 dispatch。

**推荐修正：**在进入通用 pending queue 之前增加一个很窄的“计划结果路由适配层”：

1. 先校验结果 envelope 的 task 所有权、有效 session key 与 `plan_id`；
2. `plan_id` 匹配当前活跃计划，才进入该回合的 pending queue；
3. 同会话但不匹配的合法结果进入可持久化的 deferred-result lane，不得进入当前模型消息；
4. 无归属、归属不等或伪造的结果隔离并审计，不得持久化、注入或外发。

其中“父回合已经结束时，deferred 结果何时变为可见进度”仍须定义。建议默认不自主生成用户答复；在该任务下次恢复或重规划时作为已完成证据消费。这既避免串话，也避免后台结果无上下文地打断用户。

### P0-3：任务所有权登记存在 cleanup 竞态

方案要求消费侧通过 `task_id → {parent_session_key, plan_id}` 二次校验，这是正确的；但当前 `SubagentManager` 在 asyncio task 结束后立即清掉所有运行登记。完成公告已发布但 `AgentLoop` 尚未消费时，消费者可能查不到该 task，从而错误隔离合法消息，或退化为不校验。

**推荐修正：**单独维护有界的 `pending_result_routes`：在子任务启动前写入 `{task_id, parent_session_key, plan_id, node_id, expires_at}`；公告的 envelope 带相同字段；只有成功消费、明确取消后的安全收尾或 TTL 到期时才删除。它不是第二套 subagent 生命周期，仅是结果投递的短期所有权收据。

### P0-4：完成门无法阻止“伪最终答复”流式外泄

当前 Runner 在模型生成阶段就将 token 推给渠道。即使最终回复后发现计划尚有必需节点并 `resuming=True`，用户也已经看到“完成了”的文本。对于主子并行，这会直接破坏“汇合后再整合”的承诺。

**推荐修正：**只在启用执行计划且存在未完成必需节点时，给 `AgentRunSpec`/turn hook 增加 plan-aware 的最终文本提交门：暂存候选终答，直到计划满足、明确失败或进入受控未完成状态才一次性交付。工具进度仍可按现有机制显示。feature flag 关闭时，流式路径必须逐字节保持现状。

### P0-5：`TaskFrame` 与计划缺少生命周期和重规划契约

现有文档只给出了字段，没有定义 `clarifying`、`running`、`waiting_results`、`blocked`、`completed`、`cancelled` 的合法迁移，也没有定义用户“继续”、`/stop`、子节点失败、进程重启、任务范围改变时如何处理旧计划。没有这层约束，后续“继续”会把过期任务当作唯一锚点，或让旧 `plan_id` 的完成结果被新计划误认。

**推荐修正：**明确区分跨轮 `TaskFrame` 与单轮 `ExecutionPlan`：

- `TaskFrame` 至少有 `clarifying → ready → running/waiting_results → completed | blocked | cancelled`；
- `ExecutionPlan` 是一次执行切片，完成、取消、输入发生实质变化或需要补充新事实时终止；
- 重规划产生新的 `plan_id`，只能引用旧计划已确认的节点结果，绝不能让旧计划未消费结果直接满足新计划；
- 用户显式停止与现有 `/stop` 的优先级必须写清，并且不改变 `/goal` 原有的续办语义。

## 4. P1：应在实施切片前明确的边界

| 编号 | 漏洞/歧义 | 推荐处理 |
| --- | --- | --- |
| P1-1 | `reply` 与 `clarify` 没有严格定义。自包含事实问题不该因没有 `TaskFrame` 被澄清；但若落入普通 Runner，又可能调用工具。 | 定义 `reply` 为“无工具、自包含回答”；使用同一 runtime 的受限无工具回复路径，或让结构化意图调用返回受限答复文本。二选一后测成本和质量。 |
| P1-2 | Planner 的可用容量是瞬时观察；其他会话可先占掉容量。 | spawn 失败时节点明确转为 `blocked_capacity`，按预定义规则等待、串行化或安全地回退父节点；禁止模型无限重试 spawn。 |
| P1-3 | 意图/规划调用若复用完整上下文，可能污染 provider state 或把非可信历史当指令。 | 使用数据分隔的受限提示与严格 schema；不写 assistant/provider 会话状态；只接受白名单 evidence refs。 |
| P1-4 | `Session.metadata` 无大小、版本迁移和解析失败边界。 | 使用命名空间、schema version、上限与 fail-closed 解析；损坏状态只触发澄清，不得猜测执行。 |
| P1-5 | 明确 `/goal`、内部 system 消息和普通“继续”的优先级。 | 命令与系统消息继续绕过自然语言意图层；活跃 `/goal` 维持既有逻辑，普通 TaskFrame 不得篡改其状态。 |
| P1-6 | 当前子任务公告可在缺少 `session_key` 时用 channel/chat fallback。 | 计划模式中禁止 fallback：有效父 session key 为空即拒绝启动/隔离结果；遗留模式在 feature flag 关闭时维持兼容。 |

## 5. 与基线兼容的最小修正边界

下列修正仍符合“增量桥接，而非重构”的约束：

| 保持不动 | 最小新增 |
| --- | --- |
| `AgentRunner` 的工具调用、工具注册、安全/权限和 provider 能力 | `AgentLoop` 中 runtime 预备与 no-run 收尾；Runner 仅接受通用的继续/终答提交回调。 |
| `SubagentManager` 的执行、取消、状态事件和结果公告机制 | 有 TTL 的结果路由收据、plan/node 元数据与消费确认。 |
| MessageBus、现有 pending queue、WebUI 协议 | 在 queue 前的计划结果适配与同会话 deferred lane；不改变普通消息路由。 |
| `/goal`、memory、session 压缩既有语义 | TaskFrame 命名空间和明确优先级；ready 才进入原 build/run 链路。 |

这条边界意味着：不新建调度器、不让 Runner 认识任务图、不替换 subagent 生命周期，也不新增能力权限系统；但也不能假设现有会话级回注天然就是计划级汇合。

## 6. 实施前应先补的评测

P0 修订后，至少先在 `04_评测` 建立以下可回放场景，再动运行代码：

1. 无对象澄清、无工具直答、唯一任务“继续”三种回合均正确持久化，不触发 memory consolidation 或业务工具；
2. 同 session 的计划 A 与计划 B 交叠完成，B 的结果绝不进入 A 的模型上下文；
3. 两个不同 session 的结果在任一活跃/空闲组合下都不串入对方；
4. 子任务公告与 manager cleanup 竞争时，合法结果仍可凭结果路由收据消费一次且仅一次；
5. 主子并行时，候选终答不会先流式显示为最终完成；
6. 容量被其他会话抢占、子任务失败、取消、进程恢复和重规划时，不重试风暴、不伪造完成、不误用旧结果；
7. feature flag 关闭时，普通消息、`/goal`、memory、subagent 与 WebUI 的现有回归行为完全一致。

## 7. 建议的下一步

先把 P0-1 至 P0-5 逐项吸收到桥接方案的“数据契约、运行顺序、故障降级、验收”中，并新增一份 ADR 冻结：结果路由收据、计划级 deferred lane、终答提交门与状态机。完成后再评估是否满足定案条件；在此之前不进入实现切片。
