# 上下文机制取证：任务理解改造的复用边界

**取证日期：** 2026-08-09  
**范围：** 当前工作区源码静态阅读；不包含线上运行探针  
**结论状态：** 可作为方案输入；实现前须在隔离开发基线复核

## 1. 结论

nanobot 现有上下文机制是可靠的模型输入装配层，但不是任务状态机。它适合向模型提供“本轮理解任务所需的证据”和“当前已确认任务的受控投影”；不应承担任务对象、授权、依赖关系或委派决策的唯一事实来源。

原因是原始会话会因 token 预算和闲置压缩而归档，长期记忆也由摘要维护；仅靠模型从自然语言回放中推断“这件事”会在长会话中失去确定性。

## 2. 四层上下文及其职责

| 层 | 当前实现 | 生命周期 | 可否作为任务事实源 |
| --- | --- | --- | --- |
| 系统上下文 | `ContextBuilder.build_system_prompt()`：身份、工作区规则、工具契约、记忆、技能、近期归档、压缩摘要 | 每次请求重建 | 否；它是规则与背景 |
| 会话回放 | `Session.get_history()`：最近可回放的用户、助手、工具消息 | 会受条数、token 与合法工具序列边界裁剪 | 否；它是对话证据 |
| 运行时上下文 | `RuntimeContextBlock`：本轮附加到当前用户消息的 provider 输出 | 本轮构建，且当前实现会随用户消息持久化给模型回放 | 否；它是受控投影 |
| Provider 续接状态 | `Session.provider_state` | 仅兼容 provider/model 时复用；压缩后清空 | 否；它是厂商私有优化 |

## 3. 当前装配时序

普通用户消息经 `AgentLoop._process_message()` 依次进入：

```text
restore → compact → command → build → run → save → respond
```

在 `build` 阶段，`_build_turn()` 会：

1. 按 token 预算触发 `Consolidator.maybe_consolidate_by_tokens()`；
2. 从 `Session.get_history()` 取得合法、受限的回放尾部；
3. 构造一份不可变的 `RequestContext`；
4. 解析本轮 `RuntimeContextBlock`；
5. 尽可能续接 provider 私有会话；
6. 提前持久化用户消息；
7. 用 `ContextBuilder` 生成模型请求。

当前没有 `assess` / `task-admission` 阶段：非斜杠自然语言消息会直接进入模型—工具循环。

## 4. 现有可复用能力

### 4.1 `Session.metadata`：任务状态的候选持久化宿主

`Session` 已持久化 `metadata`，现有 `/goal` 以 `goal_state` 写入此处，再由 `CreateGoalTool.runtime_context_provider()` 每轮转换成提示上下文。此模式说明可以新增**版本化的任务状态记录**，再以只读投影供模型使用。

但不能直接复用 `goal_state`：它只表达一个由 `/goal` 显式创建的长期目标，缺少自然语言锚定证据、歧义状态、多个节点及节点依赖。

### 4.2 `RuntimeContextProvider`：模型可见的受控投影通道

`AgentLoop._resolve_runtime_context_for_request()` 会以稳定顺序组合：

1. 工具自带 provider；
2. 宿主注册的 provider。

现有 provider 包括活动长期目标、CLI app 附件、WebUI 选中引用及跨会话提及。它们都采用明确边界和“metadata only, not instructions”包裹，且测试已覆盖来源顺序、长度限制和注入闭合防护。

后续任务帧可新增为一个 provider，但内容必须是：当前已确认状态的紧凑 JSON/字段投影、版本号、证据引用和本轮允许动作；不能把用户自然语言或历史摘要未经边界处理地塞入其中。

### 4.3 `RequestContext`：本轮执行的只读携带体

`RequestContext` 已将 session key、原始用户文本、渠道、消息元数据、工作区作用域和 turn id 注入工具。任务准入完成后，可在此增加或通过 `attributes` 携带**已判定的任务帧快照**，让执行和 `spawn` 工具使用同一个事实，不再自行从提示词猜测。

它不适合作为持久化任务状态：其生命周期只是一轮请求。

### 4.4 WebUI 的显式引用能力：用户主动锚定的高价值证据

WebSocket 可信 WebUI 请求可附带：

- `quoted_context`：用户选中的助手文本；
- `session_mentions`：用户明确选择的其他会话引用；
- 工作区作用域元数据。

这些应在未来的锚定器中作为高优先级证据，但“已选工作区”只是安全范围，不自动等于用户要求处理的对象。

## 5. 不能误用的边界

### 5.1 压缩后的历史不可承担任务指代

`Consolidator` 会将旧消息归档为摘要或失败时的原文片段；`Session.get_history()` 只保留一个合法短尾，闲置会话还会通过 `_last_summary` 注入压缩摘要。任务图不能只存在会话文本里，否则恢复、压缩、迁移后都可能改变其含义。

### 5.2 Runtime Context 不是私有永久存储

当前 `append_runtime_context()` 会将上下文附在用户消息上并保存 `_runtime_context` 标记；UI 与公开快照会精确去除该后缀，模型回放默认仍可见它。故任务帧投影必须短小、版本可识别、可重建，不能累积为另一份无边界历史。

### 5.3 provider 续接状态不含任务语义

`provider_state` 只服务支持会话续接的模型，压缩或不兼容模型时会被清空。任何调度或授权判断依赖它，都会造成 provider 行为差异。

### 5.4 当前工具契约与已确认规则有冲突

`tool_contract.md` 中“状态不确定时先只读发现”需要改写其适用前提：只有**对象已锚定、但该对象的状态未知**时，才允许只读发现。对象缺失或指代有多个无关系候选时，应先澄清，不能用工具去碰运气。

## 6. 对意图识别方案的直接约束

1. 在 `build` 之前增加轻量的任务准入，而不是要求主模型先自由执行再回头解释；
2. 准入读取完整可用上下文，但写入独立、版本化的任务帧/任务图状态；
3. 每轮仅将与当前执行前沿相关的状态投影为 Runtime Context，避免上下文膨胀；
4. 压缩、恢复、跨渠道/统一会话和 provider 切换后，都以任务状态重建模型所需任务上下文；
5. subagent 只能接收被准入后的工作单元与必要证据摘要，不能把“父会话全文”当作替代任务锚点。

## 7. 已核对的回归保护

- `tests/agent/test_runtime_context.py`：provider 稳定顺序、WebUI 引用限长与提示注入边界、公开历史精确去除；
- `tests/agent/test_context_builder.py`：系统上下文装配、消息合并与 Runtime Context 注入；
- `tests/agent/test_session_manager_history.py`：回放裁剪和 runtime context 的公开/模型可见差异；
- `tests/agent/test_runner_injections.py`：中途消息和 subagent 回注需要重新解析其自身运行时上下文。

这些应成为后续改造的回归基线；新增任务帧后，还需覆盖压缩前后等价、对象缺失零工具调用、歧义多候选必澄清、任务图 ready 节点推进和不满足委派条件时不 spawn。
